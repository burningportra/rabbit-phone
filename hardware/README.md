# R1 physical-button bridge

This optional root daemon bridges the two stock R1 power-button input drivers to
the foreground Rabbit Phone launcher. It does not change key layout files, hold
a wakelock, open a socket, or intercept the wheel. Wheel navigation and haptics
remain app responsibilities. Deployment and app lifecycle handling live outside
this directory.

Build with Android NDK r27.2, API 26, arm64:

```sh
"$ANDROID_NDK_HOME/toolchains/llvm/prebuilt/darwin-x86_64/bin/aarch64-linux-android26-clang" \
  -std=c11 -O2 -Wall -Wextra -Werror -fPIE -pie \
  rabbit_hardware.c -o rabbit-hardware
```

The Linux-host NDK uses `linux-x86_64` in place of `darwin-x86_64`. No additional
libraries are needed. Host-only state/parser tests run on macOS or Linux:

```sh
cc -std=c11 -Wall -Wextra -Werror -pedantic test_core.c -o /tmp/rabbit-bridge-test
/tmp/rabbit-bridge-test
```

## App protocol

The sole optional command-line argument is an absolute app files directory. The
default is `/data/user/0/com.kevtrinh.rabbitphone/files`. Its owner must be an app
UID (at least 10000), and the directory cannot be group/world writable. The app
creates `hardware-events-<nonce>` and `hardware-commands-<nonce>` FIFOs for every
foreground lease, owned by that UID, mode 0600, one link. A private, atomically
replaced `hardware-lease` regular file contains the 32-character lowercase hex
nonce. Its type, owner, mode, link count and content are checked before opening
the pair. Opened FIFO inodes are checked with fstat; final components reject
symlinks. Different foreground instances never share a FIFO inode, so Camera
cannot mask Home's reader disconnect. A client unlinks only its own pair and
removes the lease pointer only if it still names that client.

The launcher opens the events FIFO for reading only while it owns the foreground
interaction. It must close both channels on pause, destruction, or shutdown. The
daemon opens the events FIFO nonblocking, then locates `mtk-kpd` and
`mtk-pmic-keys` by kernel name, both with KEY_POWER support. Event numbers are
not assumed to remain stable across boots.
Both keys must be physically released before both EVIOCGRAB operations succeed.
Queued pre-grab events are drained, and release state is checked again. Only
then does the app receive `READY\n`. Failed acquisition closes the channels and
retries no faster than twice a second; the app reader must handle EOF/reconnect.

Events after READY are `DOWN <monotonic-ms>\n` and `UP <monotonic-ms>\n`. The
monotonic timestamps are generated by CLOCK_MONOTONIC when handled. Driver
events are combined into one logical press: a down on either driver begins it;
both drivers must report release, followed by 25 ms without a renewed down,
before UP. EV_KEY repeat value 2 is ignored. The app owns click, hold, double
click, wake UI, and haptic policy. It groups using physical monotonic timestamps;
stale taps and delayed completed holds cannot become photos or false shutdowns.

### Android assistant handoff

`RecorderAssistActivity` can be launched by Android's configured long-power
Assistant shortcut. It requires the SystemUI-held
`ACCESS_VOICE_INTERACTION_SERVICE` permission and uses normal keyguard dismissal.
Only after it is focused, interactive and unlocked does
`HardwareButtonClient.startForAssistantHold()` create a nonce-bound
`hardware-assist-<nonce>` marker before publishing the normal lease. The marker
is an app-owned mode-0600 regular file, one link, with exactly `ASSIST\n` as its
contents. The helper validates and atomically renames it to
`hardware-assist-used-<nonce>`; that tombstone prevents rearming after helper
restart. The client removes both names on stop.

This one-shot session opens both power input devices **without EVIOCGRAB**.
It reads their live key state, sends `READY`, then `HELD <monotonic-ms>` if the
original button is still held. Both drivers releasing plus the 25 ms debounce
produces `RELEASED <monotonic-ms>`. An already released button produces RELEASED
without HELD and cannot start a recording. The original UP also reaches Android,
which still owns that press. After RELEASED the input descriptors close; the
Activity closes the observer session and starts a fresh ordinary foreground
session for future wheel/button interactions.

Passive sessions accept only exact `PING\n` commands. Missing heartbeat, client
death, invalid/lost input, stale/invalid markers, or a 65-second deadline cancel
the session. `CANCEL` is accepted before READY and stops the client. No observer
remains active behind another app or keyguard, and no marker changes the normal
requirement that both buttons be released before an ordinary grab.

The supported system route is documented in Android 16's
[power policy](https://android.googlesource.com/platform/frameworks/base/+/android16-release/services/core/java/com/android/server/policy/PhoneWindowManager.java)
and [SystemUI assistant dispatcher](https://android.googlesource.com/platform/frameworks/base/+/android16-release/packages/SystemUI/src/com/android/systemui/assist/AssistManager.java).
The app uses [requestDismissKeyguard](https://developer.android.com/reference/android/app/KeyguardManager#requestDismissKeyguard(android.app.Activity,%20android.app.KeyguardManager.KeyguardDismissCallback))
without disabling credential checks.

The daemon accepts only these exact newline-terminated command lines:

| Command | Fixed action |
| --- | --- |
| `SLEEP` | Release grabs, execute `/system/bin/input keyevent 223` |
| `SHUTDOWN` | Release grabs, execute `/system/bin/svc power shutdown` |
| `MOTOR_FRONT` | Write `0` to the fixed motor orientation sysfs file |
| `MOTOR_REAR` | Write `180` to the fixed motor orientation sysfs file |
| `MOTOR_PRIVACY` | Write `90` to the fixed motor orientation sysfs file |
| `PING` | Renew the foreground UI heartbeat lease for 3000 ms |

The motor file is
`/sys/devices/platform/step_motor_ms35774/orientation`. These names assume the
provided 0/180/90 orientation contract; physical direction needs device proof.
Motor commands are limited to one accepted request per 250 ms; faster requests
are dropped. Commands have no acknowledgement, so dispatch is not proof of
successful sleep, shutdown, or rotation. Invalid lines, including CRLF,
embedded NULs, additional arguments, and overlong lines, do nothing. No command
is passed through a shell. Child processes close inherited descriptors before
work and have a three-second alarm. Actual sysfs driver behavior and SELinux
permissions require device validation.

When a camera-owned session ends, outstanding motor children finish before a
final privacy park. Input grabs are already released during that cleanup. Home
also requests privacy on reconnect; writes are skipped if position already matches.

After SLEEP or SHUTDOWN, the daemon cannot grab again for the current reader: it
waits for that events reader to close before returning to idle. The app must
therefore close its channels as part of those transitions and reopen on resume.

## Failure behavior and proof boundary

While active, blocking poll watches the event writer for reader disconnection,
both input streams, and commands, with deadlines for the 25 ms release debounce
and the heartbeat lease. The command FIFO is opened O_RDWR by the daemon to avoid
spinning on HUP when no command writer is connected. Event FIFO backpressure,
short writes, EPIPE, lost input events (SYN_DROPPED), unexpected non-power keys,
device removal, or I/O errors abandon the session and release both grabs. An
unexpected key is logged; that first event cannot be replayed to Android, so an
unexpected key may be lost before normal Android delivery resumes. No global
remapping is installed. SIGINT and SIGTERM unwind normally; SIGKILL closes the
file descriptions and the kernel releases their grabs.

The app sends PING from its main UI handler every 750 ms while active. A
background worker must never generate heartbeats on its own, or a frozen UI
could retain the button. The first lease starts at READY and expires after
3000 ms without PING. On expiration both input grabs and the command FIFO close.
Only the events writer remains open, without writes, to poll for the old reader
disconnecting; no new session can grab while that old reader remains. When a
recovered UI attempts its next PING, EPIPE must make the app close and reconnect
both channels. The app must also tie its reader to its foreground lifecycle.
There is no heartbeat activity while idle and no wakelock. The hardware
emergency-reset path, app freeze/crash/pause fail-open behavior, wake/release
race, double-driver timing, sleep, and physical orientation require live-device
checks.

Host tests cover parser boundaries, heartbeat deadlines, and dual-driver transitions;
they do not simulate the kernel grab, Android lifecycle, or device hardware.
## Startup and rollback

The root-owned executable is under `/data/local/rabbit-phone`. The tracked
`rabbit-phone.rc` uses the ROM's existing shell-to-su SELinux transition; direct
init execution of the data binary is denied. SELinux remains enforcing.
`scripts/install_hardware.py` backs up the original startup file, manages the
reviewed startup block, verifies hashes, and returns `/` to read-only.

`scripts/verify_reboot.py` requires an actual new boot, Android boot completion,
an init-managed running helper, and the intended HOME role. A manually launched
ADB process is not startup proof.
